this theme auto-converts images (including .gif) to static .webp, and figure.liquid serves that webp. So if you use {% raw %}{% include figure.liquid %}{% endraw %} (or the project card img:), a GIF shows a frozen frame, not the animation.

GIF that actually animates → use a plain <img> (bypasses the webp pipeline). Put this anywhere in a page body (404, a project's body, etc.):


<div style="max-width: 360px; margin: 1rem auto;">
  <img src="/assets/img/spiral.gif" class="img-fluid rounded z-depth-1" alt="spiral animation" loading="eager">
</div>

For a video (put the file in assets/video/):


<video src="/assets/video/demo.mp4" autoplay loop muted playsinline width="100%"></video>
--
Video (mp4/webm) → use the theme's video.liquid include (videos aren't touched by the image pipeline). Put the file in assets/video/ and:
{% raw %}{% include video.liquid path="assets/video/demo.mp4" class="img-fluid rounded z-depth-1" autoplay=true loop=true controls=true %}{% endraw %}

raw tag if you prefer full control:
<video src="{% raw %}{{ '/assets/video/demo.mp4' | relative_url }}{% endraw %}" autoplay loop muted playsinline width="100%"></video>

Why the subpages still open
published: false only unpublishes the one file it's written in — your /blog/ landing page. It has no effect on the individual blog posts, because those live in a separate collection (_posts/). Each post is its own document that Jekyll renders independently at /blog/2015/formatting-and-links/ etc. Hiding the listing page doesn't hide its "children" — Jekyll has no parent→child relationship between blog.md and the posts.

The same is true for the other hidden pages that are backed by collections:

blog.md → _posts/ (30 posts) + jekyll-archives year/tag/category pages
books.md → _books/ collection
teaching.md → _teachings/ collection
(reads.md, dropdown.md, plugins.md, profiles.md are standalone pages with no subpages, so those are already fully hidden.)

Cmd-K palette is built from content at build time, gated by _config.yml:89 posts_in_search: true. As long as the posts are generated, they get indexed regardless of the blog landing page.

Two levers: (1) turn off posts-in-search, and (2) unpublish the whole collection via _config.yml defaults — instead of hand-editing 30+ post files. Unpublished documents drop out of site.posts, so the pages stop generating and they leave the search index (empty collections also produce no archive pages). matching scope:
_config.yml. In YAML, defaults: is a list, and each - scope: … values: … entry is one item in that list — that's a "scope block." Here's what's there now:

Each collection now has its own clearly-labeled block in _config.yml, and the rule is simple:

Block uncommented → section hidden (current state for all three).
To bring a section back → comment out its 4 lines (put # in front of each), then set that listing page to published: true.
For example, to un-hide the blog, you'd turn:


  # --- BLOG (posts) : HIDDEN ---
  - scope:
      path: ""
      type: posts
    values:
      published: false
into:


  # --- BLOG (posts) : HIDDEN ---
  # - scope:
  #     path: ""
  #     type: posts
  #   values:
  #     published: false
...and set published: true in blog.md plus flip posts_in_search back to true.

Your icon: ⚛️ setting (_config.yml:18) tells al-folio to render the emoji into a tiny PNG and embed it inline as a data: URI — the image lives inside the HTML, not as a separate file with its own URL.

Browsers happily render data-URI favicons → that's exactly why you see the atom ⚛️ at the top of the tab once the page is open (your second screenshot).
Google Search and other external surfaces do NOT use data-URI favicons. Google's favicon requirement is that the icon be a real file at a crawlable URL — Googlebot fetches the href as a URL. A data:... blob is not a fetchable URL, so there's nothing for it to crawl, and it falls back to the generic globe (your first screenshot).
Replace the emoji with a real image file. Your config comment even documents this: "alternatively, provide image name in /assets/img/."

Steps:

Create a proper favicon image — a square PNG, ideally a multiple of 48px (e.g. 96×96 or 256×256). Easiest: go to favicon.io/emoji-favicons and grab the ⚛️ atom — you get a PNG that looks identical to your current tab icon.
Drop it in assets/img/ (e.g. assets/img/favicon.png).
Change icon: ⚛️ → icon: favicon.png in _config.yml.
Verify after building — view page source and confirm the tag is now <link rel="icon" href="/assets/img/favicon.png"> (a real URL), not data:....
In Google Search Console, request a re-crawl of your homepage. Google updates search favicons on its own schedule, so expect days to a few weeks — and note favicons mainly appear in mobile results.

for citation update:
You already have a pre-push hook wired up (core.hooksPath = .githooks). On git push it runs the scraper in --if-scraped mode:

Scrape succeeds and numbers changed → it commits _data/citations.yml and stops that push with a message; you just run git push again and both go up. That's what produced your "Auto-update Google Scholar citations" commits.
Scrape blocked or numbers unchanged → no-op, push proceeds. A blocked scrape can never wipe your data.
It also validates the YAML first and aborts the push if it's malformed, since a broken _data file would fail the build and silently leave the old site live.

When you want to force it by hand:


python bin/update_citations_local.py             # scrape; fall back to manual values
python bin/update_citations_local.py --manual    # skip scraping, use MANUAL_PUBLICATIONS
python bin/update_citations_local.py --if-scraped  # only write if a live scrape worked
If Scholar is 403-ing you and the count is stale, edit MANUAL_PUBLICATIONS at bin/update_citations_local.py:51-58 with the real number, run with --manual, then commit and push.
Two things worth knowing for later: on a fresh clone the hook is dormant until you re-run git config core.hooksPath .githooks
